# Plan: Standalone APK — Embedded Server on Android Tablet

## Problem

Client has **no WiFi, no PC** — only Android tablets. They need the full CaféOS system running on a tablet with local SQLite, plus a way to export the SQLite file later when they buy a desktop unit.

The PostgreSQL/Nen connection string was a misdiagnosis: it addresses data storage but **not execution**. The App Router API routes, Socket.IO server, auth middleware, and backup/restore endpoints all run in `server.js` (a Node.js process). The tablet *is* the client browser today; it cannot host the server without an embedded runtime.

## Constraint: Separate Project

Per the owner's instruction, the APK is a **separate project outside the Pebot directory**. Pebot's `my-app/` is used only as a **build source** — we run `CI=true npm run build` to produce the standalone output, but **no source files in Pebot are modified**. All APK-specific code lives in `cafeos-tablet/` (a sibling directory, e.g., `../cafeos-tablet/`).

## Recommended Approach: Capacitor + Embedded Node.js (separate project)

Package `server.js` + the Next.js standalone build inside an APK using **Capacitor** + **nodejs-mobile** (embeds a V8/Node.js runtime). The WebView loads `http://localhost:3000`. This preserves **all existing UI and business logic unchanged** — the same web app runs inside the APK.

```
cafeos-tablet/                   (separate project, outside Pebot)
├── capacitor.config.ts          (Android shell config)
├── android/                     (generated Android project)
├── assets/
│   ├── server.js                 (copied from Pebot/my-app)
│   ├── .next/standalone/          (built via `CI=true npm run build` in Pebot)
│   ├── node_modules/              (Prisma, sql.js, or Prisma engine)
│   └── prisma/schema.prisma       (same schema — ensures SQLite compatibility)
│
├── nodejs-mobile/                 (embedded Node.js runtime)
└── lib/
    └── prisma-sqlite.ts           (sql.js adapter — only if Prisma engine can't be built)
```

```
APK
├── Capacitor WebView ──http://localhost:3000──→ node.js (nodejs-mobile)
│                         │
│                         ├── server.js (Next.js + Socket.IO)
│                         ├── .next/standalone (pre-built)
│                         ├── node_modules
│                         └── prisma/schema.prisma
│
└── SQLite file (app-private storage: /data/data/com.cafeos/files/cafeos.db)
```

The UI is already mobile-ready (no changes needed):
- `app/admin/AdminLayoutClient.tsx` — has `md:hidden` mobile header + slide-in sidebar
- `app/layout.tsx` — responsive viewport settings
- `public/manifest.json` — `"display": "standalone"`, `"orientation": "portrait-primary"`

## The Database Challenge (Critical)

**Prisma's query engine is a native Rust binary.** Prisma 5.22 does **not** ship an Android (aarch64-linux-android / Bionic libc) build. `prisma-client-js` will fail to initialize inside the embedded Node.js on Android.

### Options

| Option | Approach | Pebot changes? | Pros | Cons |
|---|---|---|---|---|
| **B: Build Prisma engine for Android** (preferred) | Cross-compile `prisma-engines` Rust source for `aarch64-linux-android`, bundle the `.so` in the APK `libs/` dir, set `PRISMA_QUERY_ENGINE_BINARY` env var. | **None** — just bundle binary + env var | Zero code changes. Same Prisma API. Same SQLite file. | Requires Rust + Android NDK. Uncertain build. |
| **A: sql.js adapter** (fallback) | In the **mobile project only**, create a Prisma-compatible adapter backed by `sql.js` (pure-JS/WASM). Patch the built `lib/prisma.js` or use a build-time alias to swap Prisma for the adapter. | **None** — patching done in mobile project on built output | Works immediately. No Rust toolchain. Same SQLite file. | Must implement Prisma API subset. ~300–500 lines in mobile project. |

**Recommended: Try Option B first.** If the Prisma engine builds for Android, the APK is just a packaging exercise — zero code changes anywhere. If it fails, fall back to Option A (sql.js adapter in the mobile project, applied to the built output without touching Pebot source).

### Prisma API surface to cover (if Option A is needed)

Across all 8 repository files, the Prisma methods used:
- `findMany`, `findUnique`, `findFirst` — with `where`, `include`, `orderBy`, `take`, `skip`, `select`
- `create` — with nested `create` (e.g. `items: { create: [...] }`)
- `update` — with `decrement`/`increment` (stock adjustments)
- `updateMany`, `delete`, `createMany`, `count`, `upsert`
- `$transaction` — both array form and callback form
- `$executeRaw` / `$queryRaw` — for PRAGMA
- Filters: `in`, `lt`, `contains`, `startsWith`, `equals`, nested relation filters

## Implementation Steps

### Phase 0: Build Pebot output (no source changes)
1. From `Pebot/my-app/`: `CI=true npm run build`
   - This produces `.next/standalone/` (per `next.config.js:24`)
2. Copy `server.js`, `.next/standalone/`, `prisma/schema.prisma` into `cafeos-tablet/assets/`

### Phase 1: Spike — Embedded server boots on Android
1. Create Capacitor Android project:
   ```
   cd ../cafeos-tablet
   npx cap init cafeos com.cafeos.pos
   npx cap add android
   ```
2. Add `nodejs-mobile`:
   ```
   npm install nodejs-mobile-react-native
   # Configure android/build.gradle with node runtime
   ```
3. Create an Android `Service` that starts Node.js with `server.js` from extracted assets
4. WebView loads `http://127.0.0.1:3000` after server is ready
5. **Verify**: server boots, health endpoint responds

### Phase 2: Database — make Prisma work (or substitute)
1. **Try Option B first**: Build Prisma query engine for `aarch64-linux-android`
   - Install Rust: `rustup target add aarch64-linux-android`
   - Add Android NDK
   - Build `prisma-engines` query_engine
   - Bundle `.so` in APK `libs/arm64-v8a/`
   - Set `PRISMA_QUERY_ENGINE_BINARY` at runtime
2. **If Option B fails**: Create `lib/prisma-sqlite.ts` in the mobile project
   - Implement sql.js adapter with the Prisma API surface above
   - Use Next.js webpack alias to swap `@/lib/prisma` → adapter (applied to built output)
3. **Verify**: All existing endpoints work (orders, inventory, auth, backup)

### Phase 3: App-private SQLite
1. Set `DATABASE_URL="file:/data/data/com.cafeos/files/cafeos.db"` at startup
2. On first launch: create schema + seed data
   - Run schema from `prisma/schema.prisma` (convert to SQL `CREATE TABLE` statements)
   - Use existing `prisma/seed.ts` logic or bundle a pre-seeded `dev.db` as an asset
3. **Disable mDNS** in `server.js` when running on Android (guard with platform check in the service launcher wrapper)

### Phase 4: Export / Import (Migration Path)
1. **Export** ("Save Data"):
   - Trigger existing `/api/backup` endpoint → ZIP file with SQLite
   - Save to tablet's Downloads folder via Capacitor File plugin
2. **Import** ("Restore Data"):
   - File picker (Capacitor) → select ZIP → POST to `/api/restore`
3. **Migration compatibility**: APK's SQLite uses **identical schema** (same `schema.prisma`). Copying exported `dev.db` to desktop `prisma/` + `prisma db push` should work — **verify with test**.

### Phase 5: Foreground service + lifecycle
1. Run Node.js in a **foreground service** with persistent notification
2. Handle app pause/stop (don't kill the server)
3. Handle app kill (clean shutdown of server + Prisma disconnect)

### Phase 6: Mobile UX polish
1. Verify all admin pages render on 10-inch tablet (~1280×800)
2. Touch target sizes (minimum 44px)
3. WebView scroll containers
4. Android back button navigation
5. Input focus handling (avoid zoom)

### Phase 7: Build, test, release
1. Build debug APK → test on physical tablet
2. Verify: full POS flow, offline operation, export/import
3. Test migration: export from APK → import on desktop
4. Build release APK (sign with keystore)
5. Document sideloading instructions

## What Works Without Changes (from Pebot)

- `server.js` — binds `0.0.0.0:3000`, health endpoint at `/api/health`
- Backup/restore — file-based, works anywhere
- All API routes, Socket.IO, auth, business logic
- UI responsiveness — admin layout has mobile breakpoints
- SQLite schema — identical to desktop
- Migration format — same backup ZIP with `dev.db`

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Prisma engine won't build for Android | Fall back to Option A (sql.js adapter in mobile project). Pre-write adapter scaffold to reduce fallback cost. |
| sql.js adapter too complex | Start with order/catalog/inventory repositories (used most). Add others iteratively. |
| nodejs-mobile + Next.js incompatibility | server.js uses standard Node.js `http`/`next` — test boot first. If Next.js SSR fails, switch to static export mode with API replaced by sql.js calls (larger refactor). |
| Android kills background process | Foreground service with persistent notification. |
| APK size (~100MB+) | Accept for MVP. Document expected size. |
| Schema drift between APK and desktop | Same `schema.prisma` is copied into both. No drift possible. |
| `mdns-js` crash on Android | Guard with `try/catch` + platform check in service launcher. Already has error handling in `server.js:70-76`. |
| `bcryptjs` for password hashing | Pure JS (no native binary) — works on Android. |
| `@prisma/client` engine download | If Option B, bundle engine manually. If Option A, sql.js has no native engine. |

## Out of Scope

- Cloud sync / mobile data coordination (no WiFi → offline only)
- Customer self-ordering via QR (no public IP without WiFi)
- iOS version (user specified APK only)
- Play Store publishing (sideloading only)
- Payment gateway integration (POS records payments, doesn't process them)
- BIR accreditation (constitution explicitly excluded)
